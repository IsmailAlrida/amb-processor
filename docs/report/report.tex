\begin{abstract}
This report presents the AMB processor as a single-cycle implementation of a custom 15-bit instruction set architecture (ISA) with 28-bit data words and byte-addressable memory. The project includes two implementation tracks. The first track preserves the original Part 1 ISA in Logisim artifacts, including the opcode decoder, hardwired control worksheet, and partial datapath. The second track implements the refined processor in Verilog, integrates it with instruction and data memory models, and verifies it through a Python-based assembler and RTL simulation workflow. The Verilog core successfully executes the required array-sum benchmark, producing the value 25 at data-memory address \texttt{0x0200}. The two tracks together show both the course-required control/datapath reasoning and the more regular RTL design that made the processor practical to assemble, simulate, inspect, and explain.
\end{abstract}

\section{ISA Summary}

The AMB processor was designed around a small fixed-length ISA: 15 instruction bits are stored in a 16-bit memory slot, while all architectural data values use 28 bits. Because memory is byte-addressable, every instruction occupies two consecutive bytes and the instruction counter (IC) advances by 2 during sequential execution. The assignment calls this state the program counter (PC); in this report, IC and PC refer to the same fetch address concept.

The original Part 1 ISA used three instruction formats: a 7-bit opcode register format, a 4-bit jump opcode with an 11-bit immediate, and a 3-bit immediate format. That design met the project constraints, but it forced the control unit to treat each instruction family differently. The refined RTL keeps the same 15-bit storage rule and 28-bit machine width, but regularizes decoding by making \texttt{instr[14:8]} a 7-bit opcode for every implemented instruction.

\begin{tipbox}[IC Implementation Note]
In the first ISA draft, IC appeared as a writable register-file entry. In the refined Verilog implementation, IC is dedicated CPU state. This keeps the fetch path under one synchronous owner while still exposing IC as an output for instruction memory and waveform inspection.
\end{tipbox}

\section{RTL And Logisim Overview}

The project is presented through two complementary implementation tracks. The main processor is the Verilog RTL core, where \texttt{cpu.v} connects instruction fetch, hardwired decode, the register file, the ALU, branch logic, and the external data-memory buses. Around that core, the Python application assembles AMB assembly programs, prepares memory images, launches Icarus Verilog simulation, and opens reports or waveforms. This toolchain is not the processor itself; it is the bench around the processor, and it makes the hardware behavior visible enough to debug.

The Logisim work preserves the original ISA direction requested by the assignment. It includes the opcode decoder, hardwired control-unit table, and partial datapath. That track is useful because it documents the direct course-style design process: signals are labeled, instruction classes are separated, and the control table follows the older instruction formats. The Verilog track then shows the same processor idea after the ISA was cleaned up into a more regular hardware contract.

\begin{resultbox}[Implemented Result]
The RTL simulation executes the mandatory array-sum benchmark for \texttt{N = 5} and array \texttt{[3, 7, 2, 9, 4]}. The recorded validation run halts after 65 cycles, with expected result \texttt{0x19} and actual result \texttt{0x19} at data-memory address \texttt{0x0200}.
\end{resultbox}

\section{ISA Optimization}

\subsection{What Changed}

The most important refinement was making the opcode field constant. In the implemented RTL, every instruction uses \texttt{instr[14:8]} as a 7-bit opcode. Register operations use \texttt{instr[7:4]} as \texttt{Rb} and \texttt{instr[3:0]} as \texttt{Ra}; immediate and jump operations reuse \texttt{instr[7:0]} as an 8-bit immediate. That single decision removes much of the old decoder branching and lets the controller classify operations by direct opcode comparison.

The second refinement was replacing partial destination-register immediate loads with an immediate assembly register, \texttt{IMR}. The processor now uses \texttt{LIL}, \texttt{LIH}, \texttt{LILL}, and \texttt{LIHH} to load four byte lanes of \texttt{IMR}. A normal \texttt{MOV} then transfers the assembled value into a general-purpose or special-purpose register. It takes a few simple instructions, but it avoids a larger immediate datapath and keeps the instruction format tidy.

Memory addressing also changed. The older ISA used \texttt{MEMOFF + imm8} for \texttt{LOAD} and \texttt{STOR}. The implemented RTL uses \texttt{MEMOFF + Rb}. This makes indexed memory access natural: a program can keep a pointer in a register, load or store through it, then increment the pointer using normal ALU instructions. The array-sum benchmark benefits directly from this choice. Table~\ref{tab:format_comparison} shows the encoding shift, while Tables~\ref{tab:old_isa_full} and~\ref{tab:new_isa_full} give the full old and new instruction sets.

\subsection{Why The Refinement Helped}

The original ISA was compact, but compactness came with control cost. A mixed opcode field means the control unit must first identify the instruction family and only then interpret the remaining bits. That is manageable on paper, but in a single-cycle datapath it quickly adds multiplexers, special cases, and decode paths that are easy to wire incorrectly.

The refined ISA trades a little encoding density for a cleaner datapath. With one opcode field, instruction classification becomes a direct comparison. With \texttt{IMR}, constant construction is explicit and easy to trace. With register-indexed memory, the benchmark loop can walk through an array using ordinary pointer arithmetic. In short, the new ISA is still small, but it gives the hardware fewer ways to get tangled.

\section{Datapath And RTL Development}

The Verilog processor is a single-cycle datapath. Instruction memory provides the current instruction combinationally from \texttt{IC}; the controller decodes \texttt{opcode}; the register file exposes \texttt{Ra} and \texttt{Rb}; the ALU produces arithmetic, logical, comparison, or address results; and the selected writeback value is committed on the next rising clock edge.

The instruction counter is one of the few explicitly synchronous elements in the core. On reset, \texttt{IC} becomes zero. When \texttt{halt} is not asserted, the next clock edge loads either \texttt{IC + 2} or the branch target:
\[
\mathrm{NextIC} = \mathrm{IC} +
\begin{cases}
(\operatorname{signext}(\mathrm{imm8}) + \mathrm{JMPOFF}) \ll 1, & \text{long or conditional jump taken} \\
\operatorname{signext}(\mathrm{imm8}) \ll 1, & \text{plain jump taken} \\
2, & \text{sequential execution.}
\end{cases}
\]
The left shift by one converts an instruction offset into a byte offset because each instruction occupies two bytes.

The register file uses asynchronous reads and synchronous writes. This is well suited to a single-cycle teaching processor: source operands are visible during the cycle, and the result lands in the destination register only at the clock edge. The same writeback port handles ALU results, memory loads, and immediate-byte writes into \texttt{IMR}. For \texttt{IMR}, the \texttt{ImmSel} control signal selects which byte lane is updated.

The data memory is byte-addressed but transfers 28-bit words. Reads are asynchronous and return four bytes assembled little-endian, with the upper nibble of the fourth byte used for bits 27--24. Stores are synchronous and split a 28-bit value back across four byte locations. This is why the benchmark uses a stride of 4 when iterating over the array.

\noindent The writeback selector is encoded as \texttt{RegDest = 00} for data memory, \texttt{01} for ALU result, and \texttt{10} for the zero-extended immediate byte. The \texttt{ImmSel} field selects the \texttt{IMR} byte lane: \texttt{00} for bits 7--0, \texttt{01} for bits 15--8, \texttt{10} for bits 23--16, and \texttt{11} for bits 27--24.

Branch control is deliberately explicit. For \texttt{JPEQ} and \texttt{JPBLW}, the CPU overrides the normal instruction register selects and reads \texttt{CMPA} and \texttt{CMPB}. The ALU continuously computes equality and unsigned less-than flags, and the branch unit selects the next IC only when the selected condition is true. This avoids hidden condition-code state and makes branch behavior easy to see in a waveform.

\section{Instruction Execution And Benchmark}

The mandatory benchmark sums five words from memory:
\[
3 + 7 + 2 + 9 + 4 = 25 = \texttt{0x19}.
\]
The data layout follows the assignment prompt: \texttt{LEN} is stored at \texttt{0x0100}, the array begins at \texttt{0x0104}, and the result is written to \texttt{0x0200}. Since each AMB data word occupies four bytes in the byte-addressed data memory, the loop increments the array pointer by 4 after every load. Listing~\ref{lst:array_sum_source} is the same benchmark source loaded by the app through its sample-code path.

\begin{lstlisting}[caption={Array-sum benchmark assembly source loaded by the app.},label={lst:array_sum_source}]
// Array sum benchmark
// N = 5
// ARRAY = [3, 7, 2, 9, 4]
// RESULT should become 25 at address 0x0200.

// R0 = sum
// R1 = LEN pointer
// R2 = len
// R3 = index
// R4 = 1
// R5 = 4-byte word stride
// R6 = array/result pointer
// R7 = current element

// Load LEN into R2
LIL 0x00
LIH 0x01
MOV R1, IMR
LOAD R2, R1

// Intialize sum and index registers as 0
LIL 0x00
LIH 0x00
MOV R0, IMR
MOV R3, IMR

// Set R4[0]
LIL 0x01
LIH 0x00
MOV R4, IMR

// R5 as 4 to use for striding 4-bytes in memory
LIL 0x04
LIH 0x00
MOV R5, IMR

// Load array start location to R6
LIL 0x04
LIH 0x01
MOV R6, IMR

// Loop across
loop:
MOV CMPA, R3
MOV CMPB, R2
JPBLW body
JMP done

// Loop while the index is less than the length
body:
LOAD R7, R6
ADD R0, R7

// Stride forward
ADD R6, R5

// Increment loop counter
ADD R3, R4

// Repeat
JMP loop

// Finish when index (R3) == len (R2)
done:
LIL 0x00
LIH 0x02
MOV R6, IMR
STOR R0, R6
HLT
\end{lstlisting}



The program first builds the required constants through \texttt{IMR}, then copies them into working registers. The loop uses \texttt{R0} as the running sum, \texttt{R2} as the length, \texttt{R3} as the index, \texttt{R5} as the four-byte stride, \texttt{R6} as the data pointer, and \texttt{R7} as the current element. Before each conditional branch, \texttt{R3} and \texttt{R2} are moved into \texttt{CMPA} and \texttt{CMPB}; \texttt{JPBLW} continues the loop while the index is below the length.

Figure~\ref{fig:rtl_result_waveform} shows the final store transaction. In this cycle, \texttt{STOR R0, R6} uses \texttt{R0} as the value source and \texttt{R6} as the address source. Because \texttt{MEMOFF} is zero for this benchmark, the ALU address calculation is \texttt{0 + 0x0200}. The ALU result therefore drives \texttt{DataAddress = 0x0200}, while the data-memory write bus carries \texttt{0x19}. The value is committed only when \texttt{DmemWriteEn} is asserted.

\section{Integrated App Workflow}

The Python application exists to make the RTL processor easier to use, not to replace it. It provides an editor for AMB assembly, assembles source code into instruction-memory hex, prepares data-memory images, runs the Verilog testbench, and opens the generated result summary and waveform files. The app can be installed from the project \href{https://github.com/IsmailAlrida/amb-processor/releases/tag/latest}{GitHub releases page}.

To reproduce the benchmark, open the app, load the sample code, select the array-sum benchmark, and assemble the program. The sample also preloads the data memory with the required benchmark data, so the assembly program can focus on the processor behavior rather than manually constructing the array. After assembly, running the RTL simulation launches the Verilog testbench in the background and produces a report containing the final result, cycle count, halt status, and generated waveform artifacts.

For deeper inspection, the waveform viewer exposes the same internal signals used in this report: \texttt{IC}, \texttt{instr}, \texttt{opcode}, \texttt{RegWrite}, \texttt{RegDest}, data-memory enables, \texttt{DataAddress}, ALU operands, ALU result, comparison flags, and branch decisions. This gives the demonstration a useful split: the app shows that the program works, and the waveform shows why it works.

The main implementation lesson from the Logisim path is that the original encoding made the wiring heavier than it needed to be. The revised RTL ISA removes that pressure by making opcode decoding regular, moving immediate assembly into \texttt{IMR}, and turning memory addressing into normal register-based pointer arithmetic.

\section{Reflection}

The AMB processor started as a compact custom ISA and became a working single-cycle RTL processor with an integrated assembler and simulation workflow. The completed Verilog design satisfies the core computer-architecture behavior expected from the project: instruction fetch, PC progression, register updates, ALU execution, memory load/store behavior, branching, halting, and benchmark execution.

The main limitation is that the Logisim implementation did not reach the same level of completion as the Verilog implementation. Still, the Logisim artifacts document the original control logic and show the required course-level datapath construction. The more complete result is the refined RTL processor: it is smaller to decode, easier to test, and much easier to explain from waveforms. That is the version we would carry forward for further ISA experiments, more benchmarks, and eventual synthesis-oriented cleanup.
